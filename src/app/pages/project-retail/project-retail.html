The problem

A retail order arrives over HTTP. It has to be accepted fast — a 202 in milliseconds — and then processed asynchronously, so a slow inventory reservation or a downstream hiccup never blocks the caller. Reserving stock, persisting the order and notifying subscribers all happen off the request path.

That buys throughput and resilience, but it creates two hard problems: making an asynchronous backend feel live to the operator watching an order, and isolating failure so one poison message can't sink the pipeline. The whole thing had to stay serverless, pay-per-use, and fully described in Terraform.

Architecture — an async event pipeline

Three repositories, one contract. A React dashboard, a set of esbuild-bundled Lambdas behind an HTTP API, and the Terraform that provisions them. Orders flow forward through a queue; the dashboard tracks state by polling — no socket server required.

retail-serverless-web

React + Vite dashboard. A seeded inventory + cart in demo mode; checkout submits through the 202 → poll → stepper pipeline and renders a per-store fulfillment plan.

retail-serverless-api

Node 20 + TypeScript, AWS SDK v3, esbuild-bundled handlers: ingest, process (SQS-triggered, idempotent), status and list.

retail-serverless-infra

Terraform modules — api, lambda, queue (SQS + DLQ redrive), topic, table, observability — composed per environment with an OIDC CI pipeline.

Inside the product

Decisions & trade-offs

Accept fast (202), process async

The ingest Lambda validates, writes the order as received, enqueues it and returns 202 immediately — the real work runs off the request path. The trade-off is that the client never gets the final result in the creating request, which the dashboard solves by tracking each order to a terminal state.

esbuild-bundled Lambdas

Handlers are bundled and tree-shaken with esbuild into tiny dist/ zips. Smaller artifacts mean shorter init duration and faster cold starts — the same optimization that was a measurable win in production. The cost is a build step the infra repo depends on.

Idempotent worker + DLQ redrive

SQS is at-least-once, so the process Lambda is idempotent — safe re-delivery, no double reservation. The queue's visibility timeout is ≥6× the handler timeout, and after three failed attempts a message lands in orders-dlq behind a CloudWatch alarm rather than poisoning the pipeline.

Single-table DynamoDB

One on-demand table holds every order, with a GSI for the recent-orders list. On-demand capacity suits spiky, pay-per-use retail traffic; single-table keeps access patterns explicit. The trade-off is that new query shapes need deliberate key/GSI design up front.

HTTP API over REST API Gateway

The API uses API Gateway's HTTP API, not the older REST API — lower latency, lower cost and far less config for a straightforward CRUD-plus-ingest surface. I'd only reach for REST API if I needed its request validators, usage plans or edge features.

ARM / Graviton + OIDC CI

Lambdas run on ARM/Graviton for better price-performance. Deploys go through GitHub Actions with OIDC — short-lived role assumption, no long-lived AWS keys in CI: plan on every PR, apply on main, least-privilege IAM throughout.

Optional cross-project pickup optimizer

Behind a feature flag, a completed order can be optimized by my genetic-algorithm service: the real order and real store inventory are sent as an explicit scenario, and the WebSocket stream's final plan is compared against a naive nearest-store baseline. Both projects stay fully independent — neither depends on the other.

What I'd change at scale

  • Step Functions for multi-step orders — replace the single process Lambda with an orchestrated workflow (reserve → charge → fulfill) with built-in retries and compensation.
  • EventBridge as the event backbone — publish order events to a bus so new consumers (analytics, fraud, loyalty) subscribe without touching the pipeline.
  • Provisioned concurrency on the hot paths to erase cold starts under sustained load, sized from the CloudWatch init-duration metrics.
  • Multi-region active-active with DynamoDB global tables and health-checked routing for resilience and locality.
