The problem

Colombia's public data on violence is abundant but scattered and shapeless: five decades of armed conflict in one institution's archive, police crime statistics in another, coca cultivation in a third — each keyed differently, aggregated differently, and none of them watchable. The question this project answers: can you make eight decades of hard data explorable by anyone, honestly, in the browser, with no backend and no API keys?

The answer is timeline-first: the whole data model is time-indexed, the map is just its projection at year T. Drag from 1947 to 2026 and watch violence appear, spread, peak around 2002, and recede after the 2016 peace accord — municipality by municipality.

Architecture — ETL once, animate forever

A build-time ETL does all the heavy lifting; the deployed site is pure static files. Every source is normalized to one join key (the 5-digit DIVIPOLA municipality code) and one shape: {{ '{' }} code → {{ '{' }} year → value {{ '}' }} {{ '}' }}, sparse and gzip-friendly.

  • One join key, four disguises. Sources key the same municipality as cod_muni, 8-digit codigo_dane, código_dane_de_municipio, or MPIO_CCNCT — some as numbers that eat leading zeros. Everything normalizes to a zero-padded 5-digit string, and a test suite asserts zero silent orphans per layer.
  • The crosswalk that wasn't needed. The plan feared decades of municipality splits/renames would break the historic join. Measured: orphan volume is 0.7–1.8%, and it's department-level "municipio not established" sentinels — reported in the provenance panel, not hidden.
  • Fixed color breaks per layer. Quantile breaks are computed over all (municipality, year) values once, so a municipality's shade is comparable across the whole timeline — the map never re-normalizes per frame.

The timeline is the product

The scrubber spans each layer's true range — crime from 2003, conflict from 1947. A national trend sparkline rides above it with the cursor dot glued to the curve, and the 2016 peace accord marked. Hit play and the map animates year by year through MapLibre feature-state — no layer rebuilds, no re-parse, just a recolor per frame.

Two honesty mechanisms keep the animation truthful: per-100k normalization (DANE population, 2005–2026) so the map shows risk instead of population size — Bogotá is #1 in raw theft but #2 per capita — and explicit no-data rendering: a grey municipality means "not reported", never "zero".

Inside the atlas

Decisions & trade-offs

Build-time ETL over a backend
All aggregation happens server-side on Socrata (SoQL $group) at build time, then ships as ~2 MB of sparse JSON. The runtime needs no keys, no server, no CORS — it cannot go down and costs nothing. Trade-off: data freshness requires re-running the ETL (a scripted, idempotent step).
Perpetrator data, aggregated across years
Per-year, per-municipality perpetrator counts are often 1–2 cases — too sparse to read and easy to over-interpret. The breakdown panel aggregates a municipality's full history and labels both the range and the classification source (CNMH). Ethics beats granularity here.
DOM markers instead of a glyph server
MapLibre text labels need font glyph tiles — an external dependency. City labels are HTML markers revealed by zoom instead: key-less, and collision is managed by showing 5 nationally and more as you zoom.
An inset instead of distorted geography
San Andrés y Providencia is genuinely tiny and 720 km offshore. Rather than inflate it, a second MapLibre instance renders an enlarged inset sharing the same data, colors and selection — the main map stays proportional.

What I'd change at scale

  • Lazy-load layer files per group instead of up-front (~2 MB raw today, fine gzipped; not fine with monthly granularity).
  • Month-level periods where sources support them, with a year-level rollup for the zoomed-out view.
  • Vector tiles for the geometry once sub-municipality drill-down (Bogotá localidades) lands.
  • A scheduled CI job re-running the ETL so the atlas tracks the sources without manual refreshes.
