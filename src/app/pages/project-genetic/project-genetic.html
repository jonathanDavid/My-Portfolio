The problem

A genetic algorithm is a black box: parameters go in, an answer comes out, and it's hard to believe — or to teach. The goal here was twofold: make the optimization visible, so a visitor who has never heard of a GA can watch a population converge and understand what fitness means; and prove it works — that the evolved solution actually beats the naive strategies a person would reach for.

The flagship scenario is deliberately concrete: one customer, one shopping list, several stores across a city each stocking a subset of products at their own prices. A genome assigns every needed item to a store that stocks it; fitness is the negative of total cost — route · kmCost + itemCost + stores · stopPenalty. Fewer stops, a shorter drive and cheaper items all win.

Architecture — stream every generation, draw at 60fps

Two repositories, one contract. The whole design turns on one idea: the network arrival rate and the render rate are decoupled. A run emits 30+ generation frames per second; React must never re-render on any of them.

genetic-visualizer-api

Python 3.12 + FastAPI + uvicorn. A clean ga/ package — a pluggable Problem protocol, a numpy-vectorized engine, and an async runner that yields one event per generation with backpressure-aware throttling.

genetic-visualizer-web

React + Vite + Canvas 2D. A hot tier draws imperatively at 60fps off an onFrame fan-out; a throttled story tier renders the map, store cards, timeline and comparison. A Web Worker runs the same GA offline so the site is demoable with no API.

Inside the product

Does it actually beat naive?

The comparison mode is the whole point — it scores the GA's plan against the two strategies a person would reach for, on the same cost model. On the pinned scenario:

Random baseline
Greedy (nearest) −2% vs random
Genetic algorithm −23% vs random · −21% vs greedy

Honest by design: when a shopping list is genuinely single-store fulfillable, there is nothing to consolidate — the UI says "already optimal" rather than inventing a fake saving.

Decisions & trade-offs

Stream per generation, throttled

The API pushes one WebSocket message per generation (capped at ~30/s for long runs) instead of only returning the final answer — that stream is the visualization. It also powers the animation-speed control: the run computes at full speed while playback drains a buffer at 0.5×–Max. Nothing is dropped, only delayed.

numpy-vectorized fitness

The GA core is numpy, not Python loops — population fitness is evaluated as vectorized array math, which keeps generations cheap enough to stream in real time. The trade-off is expressing each Problem's fitness in array terms rather than a simple per-genome function.

Canvas + rAF, not React per generation

A React reconcile per frame at 30–60 gen/s would drop frames and thrash the GC. The hot tier (fitness chart, diversity meter) draws imperatively to canvas on a single requestAnimationFrame loop; the cost is that those visuals live outside React, contained in a small imperative store + onFrame seam.

Two-tier consumption

Store cards, timeline and the comparison need React for layout, but only ~3 updates/s. They read a throttled snapshot instead of joining the hot path, so they stay up to ~350ms behind the canvases — a gap CSS transitions mask completely.

A pluggable Problem protocol

The engine knows nothing about retail. A Problem interface — random_genome, fitness, crossover, mutate, render_spec — lets shelf-allocation and the pickup scenario share one GA. Adding a new optimization problem is a new class, not an engine change.

An explicit scenario — optimize a real order

The pickup problem accepts an explicit scenario, not just a seeded one, so the retail backend can send its actual order and store inventory to be optimized. Same fitness law, same shapes — the integration is real, and both projects stay independent.

What I'd change at scale

  • Island model — evolve several sub-populations in parallel and migrate elites between them, escaping local optima that a single population gets stuck in.
  • Ray / Celery workers — move GA runs off the API process onto a distributed pool; the frontend already treats frames as an opaque stream, so nothing changes client-side.
  • Persisted, replayable runs — store a run's seed + params behind /runs/:id so a converged run is a permalink, replayable deterministically with no live compute.
  • Windowed decimation — for thousands of generations, aggregate into min/max/avg buckets so the chart stays O(pixels), not O(generations).
